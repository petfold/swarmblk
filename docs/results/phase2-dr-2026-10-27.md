# Disaster-recovery rehearsal — 27 October 2026

A rehearsal of Phase 2's gate: a machine's host is killed, and the machine boots elsewhere from its disk card (`swarmblk card`, `swarmblk boot`, SPEC §12). Both "hosts" were state directories on laptop A, because node B, the second laptop, was offline: it answered neither ping nor ARP. Host B therefore read through node A's Bee, from a state directory that had never seen the disk and held no lineage key. The gate itself still needs a second machine with QEMU.

Times are UTC, on 26 October (local time was past midnight).

## Host A

A CirrOS 0.6.3 disk on the user guide's snapshot `3cd3aa9c…`, served writable by `swarmblk serve -disk dr` through node A, with QEMU (q35, BIOS, 512 MiB) running on it. The guest's seed wrote a random token to `/root/dr1.txt`, and 45 s later a second one to `/root/dr2.txt`, syncing after each.

## Host B

`swarmblk boot -batch … dr.card -- -drive file=seed2.img,…` in an empty state directory, from 20:31:30. The second seed printed both files and powered the guest off.

- **The machine came back whole.** Its console showed `DR READ` with both tokens, so boot took the lineage's head, update 1, and not the card's update 0: a card made before the last checkpoint still recovers it.
- **37 s in all:** boot returned 37 s after it started, with the head lookup, a full hydration of the 128 MiB disk, the guest's boot and power-off, and the final checkpoint done.
- **A new branch, not a second writer.** The card holds no lineage key, so the recovered disk's checkpoint started its own lineage on the head.

## UEFI

A second card, for the same lineage, with `firmware: "uefi"` and host A's UEFI variables (540,672 bytes, from an earlier UEFI boot of the disk) took 137 chunks. `boot` in another empty state directory chose OVMF's 4 MiB build, whose variables have that size, and wrote the variables to `disks/dr-uefi/vm/nvram.fd`. OVMF loaded its first boot entry from the NBD disk, and GRUB started 11 s in; the guest then wrote 364 KiB to the disk. CirrOS prints nothing on the serial console under UEFI, with q35 or pc, through swarmblk or from a plain local copy, so its later output could not be seen.

Then boot got SIGTERM. It pressed the machine's power button through QEMU's monitor and waited; CirrOS ignored it, so boot stopped QEMU after 2 minutes, as designed, and exited cleanly.

Two runs before these failed in the guest, not in swarmblk: with 256 MiB, CirrOS's kernel could not load under OVMF (`EFI stub: ERROR: Failed to allocate usable memory for kernel`).

## Not covered

- **TPM state.** swtpm is not installed on laptop A, so the vTPM path ran only against the fake swtpm of `TestCardBoot`.
- **Another machine.** Both hosts shared laptop A and node A's cache; the restore through node B's network path waits for the gate run.

## Cost

All 374 chunks were stamped through node A with the test batch: the two checkpoints on host A, both cards and host B's checkpoint. The batch's fullest bucket went from 24 to 25 of 32.
