# Guest-agent freeze — 26 October 2026

The first live checkpoint with a real QEMU guest agent (`serve -qga`, SPEC §8). The CirrOS guest of the [live checkpoints](phase2-live-2026-10-26.md) has no agent, so this run used the Ubuntu 24.04 guest of the [crash test](phase2-crash-2026-10-26.md), whose image has `qemu-guest-agent` 8.2.2.

## Run

`swarmblk serve -disk -batch … -qga` served a new writable disk on the crash test's ext4 base, on node A. The guest got the agent's virtio-serial channel and ran the crash test's workload on the disk: files created, a file overwritten in place and files deleted, each fsynced and committed in a log, 20 ms apart. Five seconds in, with 130 operations reported, `swarmblk checkpoint -disk` asked serve for a checkpoint.

- The agent froze the guest's filesystems, serve cut the writes, and the agent thawed them. The checkpoint took 28 s in all: 2,752 blocks changed, 2,759 chunks uploaded in 7 s and synced 22 s later, published as update 0 of a new lineage, snapshot `66eaafcc…`.
- The guest went on writing: it had reported 849 operations when the checkpoint returned, and 974 five seconds later. The agent then reported the filesystems thawed.

## Checks

1. **The snapshot says so.** Its `meta.json`, read through Bee's `/bzz`, has `consistency: "application"`.
2. **The filesystem needs no recovery.** The freeze flushed ext4's journal, so in the exported snapshot `needs_recovery` is off, and `e2fsck -fn` is clean without replaying anything. A crash-consistent snapshot from the crash test's live checkpoints, taken without a freeze, has `needs_recovery` set, and its journal must be replayed on mount.
3. **The files are all there.** The crash test's checker verified the snapshot: fsck clean, 134 operations committed (the 130 reported before the request, and 4 more before the cut), 50 files and all 256 slots of the overwritten file intact, nothing in doubt.
