# Phase 0 results — 25 October 2026

The [runbook](../PHASE0.md) with the 8 GiB Ubuntu image, run after the [CirrOS dry run](phase0-2026-10-25-cirros.md) of the same day.

## Setup

- **Node A:** Bee 2.8.3 light node on the machine that runs QEMU (7 GiB of RAM, 8 cores), with Gnosis RPC `rpc.gnosischain.com`. It holds the upload, pinned.
- **Node B:** Bee 2.8.3 light node on a second laptop on the same Wi-Fi, reached through an SSH tunnel.
- **QEMU:** 8.2.2 with KVM.
- **Image:** the Ubuntu 24.04 cloud image of 2026-10-17 as a raw image resized to 8 GiB (3 intermediate levels, root fan-out 128), with a NoCloud seed made by `cloud-localds`.
- **Batch:** immutable, depth 21. Locally, Bee's pipeline found 433,854 distinct chunks with the fullest bucket at 19, so depth 22 was not needed.
- **Deviations from the runbook:**
  - The guest got 2 GiB of RAM instead of 4, since this host has 7 GiB.
  - cold-la ran once and cold-nola not at all (observation 1).

**Upload:** 8 GiB in 2,309 s (3.7 MB/s), pinned, at redundancy level 0. The tag showed split 2,113,665 and seen 1,679,811; `synced` reached 433,854, exactly split minus seen, 44 minutes after the upload ended. Bee's root, `8ebdfc89…`, equals the root built locally with Bee's pipeline before the upload.

## Observations

1. **Stock tools cannot cold-boot this image through a light node; every cold boot failed.**
   - **cold-la:** GRUB spent about 15 minutes loading the kernel and initrd, about 75 MB at roughly 1.7 s per 128 KiB request, one at a time. systemd started about 23 minutes in. Its 90 s wait for the `/boot` and `/boot/efi` devices then ran out, and the boot fell into emergency mode at about 30 minutes.
   - **cold-tree,** with the tree cached on node B, halved the boot loader phase to about 8 minutes and reached systemd sooner. Its parallel phase then slowed reads to 5–8 s, and the same timeout ended it at 14 minutes.
   - **cold-tree-ra:** Bee cut off a 1 MiB response after 512 KiB, probably because a fetch for its lookahead failed. QEMU passed this on as an I/O error, and systemd froze at about 11 minutes.
   - cold-nola, three times slower per request, would have failed the same way, so it was not run.
2. **Bee's lookahead multiplies the work.** A 128 KiB request fetches up to 1 MiB, so with QEMU's 8 requests in flight about 2,000 chunks were wanted at once from a node that serves about 200 a second. The chunk probe's 8,000 leaves and tree walk cost node B 0.004 xBZZ, while one cold-la boot cost 0.14 xBZZ, mostly for lookahead and for re-fetching the tree on every request.
3. **A light node serves a cold chunk in about 0.3 s, and up to 214 chunks/s (0.9 MB/s) with 128 requests in flight,** with no failures in 8,000 fetches. Throughput still grew from 32 to 128 requests here, unlike in the CirrOS dry run.
4. **The boot working set is small enough to prefetch.** 78,614 blocks at 214 chunks/s take about six minutes when fetched in parallel. That suggests an engine with a cached tree and a recorded boot trace could boot this image cold in about six or seven minutes through one light node, and faster with more bandwidth. It is an estimate for Phase 2 to test.
5. **Warm and hot boots took 59.5 s and 15.8 s,** the floor on this host. The hot boot also benefits from cloud-init skipping its once-per-instance steps.
6. **The tree format holds for a real image.** Bee's `/bytes` upload gave the root that its pipeline builds locally (SPEC §14, I1), and once synced the tag shows `synced` = `split` − `seen`.
7. **Costs:**
   - The batch: 0.749 xBZZ in all, 0.177 for the first day at depth 19 and 0.572 to top up and dilute to depth 21.
   - Node B's bandwidth for these runs: 0.279 xBZZ. That is 0.140 for cold-la, 0.004 for the probe, and 0.135 for caching the tree and the two cold-tree boots. 1 xBZZ was moved from node B's wallet to its chequebook along the way.

## Proposed gate and decision

The gate has two parts, and Peter sets the cold-boot bound.

- **Working set: passes.** 307 MiB, 17% of the image's data, which can be fetched in about six minutes in parallel through one light node.
- **Cold boot: fails with stock tools.** Booting through QEMU's HTTP driver never completed, so no bound is met. What failed is the stock read path: lookahead amplification, a tree re-fetched for every request, one request at a time in the boot loader, and errors cut off mid-response. These are exactly what the engine's tree cache, parallel verified fetches and trace prefetch replace (DESIGN §3).

Proposed decision: go on to Phase 1, whose data model does not depend on these numbers. Treat the Phase 2 engine as required for cold boots, and set the cold-boot bound when an engine prototype can be measured against the six-minute estimate. A cheap check before then would be to fetch the warm boot's trace, 78,614 blocks, in parallel through node B and time it.
