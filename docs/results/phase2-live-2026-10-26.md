# Live checkpoints — 26 October 2026

First live checkpoints (ROADMAP Phase 2): the CirrOS disk of the [Phase 1 gate](phase1-gate-2026-10-26.md) served writable on node A (`swarmblk serve -disk live1 -batch …` on snapshot `99ec1706…`), with the guest booted straight from the NBD export. The guest wrote a marker, then rewrote a 4 MiB file 40 times, a second apart and with a `sync` after each, then wrote a second marker and powered off. `swarmblk checkpoint -disk live1` asked serve for a checkpoint after the fifth rewrite, while the guest kept writing, and again after it powered off.

The lineage is `0xa8eda163…/480a83b2…`, new: this host does not hold the gate lineage's key in the disk's state directory. The first checkpoint ran from 25 s to 82 s after the guest started; meanwhile the guest did its 6th to 40th rewrites, wrote its second marker and powered off. Afterwards the disk held only epoch 3, empty, on the second snapshot.

## Checks

1. **The last snapshot is the disk (I7).** The disk read back over NBD after the second checkpoint and the export of `cd080b74…` through node B, from an empty store, have the same sha256 (`dd9735c0…`).
2. **The live snapshot is crash-consistent.** In the export of `68cc6487…`, the ext3 root replays its journal as after a power cut. `e2fsck` then fixes only the free block and inode counts, and a second `e2fsck -fn` is clean. It holds the first marker and the 4 MiB file at full size. The disk as served after power-off needs the same replay, so CirrOS's power-off evidently leaves its root mounted.
3. **The lineage boots.** `swarmblk serve` of the lineage through node B, from an empty store, resolved update 1 and booted the guest from an overlay in 27.6 s (6,759 chunks fetched). It printed both markers.

The guest-agent freeze (`serve -qga`) was not run here, since CirrOS has no guest agent; `TestGuestAgent` covers it against a fake agent, and it was run later with Ubuntu's ([results](phase2-qga-2026-10-26.md)).
