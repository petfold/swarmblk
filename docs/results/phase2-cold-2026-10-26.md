# Cold boots through the engine — 26 October 2026

Phase 0 left the cold-boot bound to be set once an engine prototype could be measured. This is that measurement, on a disk that no node had fetched before: Alpine Linux booted from Swarm through the engine (`swarmblk serve`), with and without its boot trace prefetched.

## Setup

- **Disk:** Alpine 3.24.1, the generic x86-64 BIOS image with cloud-init (download checked against its SHA-512), as a raw image resized to 256 MiB. Imported on node A: snapshot `392b2485…`, disk root `2b298640…`, 41,006 chunks, synced 5 min 24 s after the import began.
- **Guest:** QEMU 8.2.2 with KVM, 1 GiB of RAM, 2 vCPUs, a NoCloud seed. A boot ends when the login prompt appears on the serial console.
- **Trace:** recorded with `serve -record` from a boot out of node A's store, which held every chunk: 18,027 blocks (70.4 MiB) in 1,445 runs.
- **Cold runs:** the engine on laptop A read through node B, a Bee 2.8.3 light node on laptop B over an SSH tunnel, which had never fetched this disk. Each run started with an empty engine store, and `-nocache` kept node B from caching what it retrieved. Runs alternated, so that warming along Swarm's retrieval paths would show as a trend. Prefetch used half of the engine's 64 fetches: 32 in flight.

## Results

| Run | Prefetch | Boot to login | Chunks fetched from Bee |
|---|---|---|---|
| local disk | — | 27.3 s | — |
| engine, store holds every chunk | — | 26.7 s | 0 |
| cold 1 | none | 1,088 s (18.1 min) | 18,036 |
| cold 1 | trace | **210 s (3.5 min)** | 17,992 |
| cold 2 | none | 1,001 s (16.7 min) | 18,110 |
| cold 2 | trace | **204 s (3.4 min)** | 17,994 |

Node B's chequebook paid 0.052 xBZZ for the four cold boots, about 290 MiB of retrievals: 0.18 xBZZ per GiB, with the free allowance.

## Observations

1. **Prefetch makes a cold boot five times faster.** Without it the guest waits for one retrieval per read: 18,000 chunks at about 57 ms each. With it the boot is bound by throughput: about 88 chunks/s with 32 fetches in flight, so the 70 MiB working set arrives in about 3.5 minutes.
2. **The two models of DESIGN §3 hold.** Cold boot is the dependent-read chain times retrieval latency without prefetch, and bytes read divided by parallel throughput with it.
3. **The second pair ran 3–8% faster,** probably from chunks cached along the retrieval paths, as Phase 0 also saw.
4. **More fetches in flight may go faster.** Phase 0 reached about 170 chunks/s through one light node with 256 in flight; at that rate this boot would take about 2 minutes, and Phase 0's Ubuntu working set (307 MiB, about 78,000 chunks) about 8 minutes.

The bound itself is Peter's to set from these numbers.
